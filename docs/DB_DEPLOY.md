# Database deployment from the repo

The deploy workflow (`.github/workflows/deploy.yml`) applies SQL to the auth database (`auth-db` container on aretea) through a
runner, `src/auth/db-deploy.sh`. Nobody runs SQL by hand on aretea. Two kinds of file are applied:

- **migrations**: `src/auth/migrations/NNNN-name.sql` (schema; additive; non-recursive, lexical order; `migrations/down/` and the
  seed `.tsv` are never candidates);
- **renumber scripts**: top-level `content/_renumber/*.sql`, generated by `just rebuild-carnet` (they remap paragraph IDs in
  `paragraph_reports` and `paragraph_stars`). Subfolders are ignored. Applied in commit-topology order
  (`git log --reverse --topo-order --diff-filter=A`; same-commit ties by natural sort, `x.sql` < `x-2.sql`), never by clock.

## The chain

The ssh step runs one remote command after the existing `git fetch` + `git reset --hard origin/main` (the checkout is unshallowed
once if needed; the runner refuses a shallow checkout). Everything is chained with `&&`: any failure stops the chain and fails the job.

```
1. GIT_COMMIT=<sha> bash src/auth/db-deploy.sh migrations        schema first; old container still serving
2. cd src/frontend && <build env> docker compose build           old container still serving
3. GIT_COMMIT=<sha> bash ../auth/db-deploy.sh renumber           ONE transaction, right before the swap
4. { docker compose up -d --force-recreate || { sleep 10 && docker compose up -d --force-recreate; }; }   swap, one automatic retry
```

`<sha>` is `GITHUB_SHA`, passed through the step's environment. The paths filter includes `src/auth/migrations/**` and
`src/auth/db-deploy.sh`, so a migration-only push also rebuilds the frontend (acceptable). There is **no "skip DB" input**:
skipping step 3 while scripts are pending would desync the site from the database.

**Dry run.** Run the workflow manually (Actions > Deploy Frontend > Run workflow) with `db_dry_run` ticked. It does the fetch/reset,
then `migrations --dry-run` and `renumber --dry-run` only: the plan is printed (pending / skipped / seed rows that would be
recorded), nothing is applied, built or swapped. A dry run still resets the deploy checkout (and prunes images and build cache, as the
workflow always does) but touches neither the running site nor the database. (A dry run on a database without a ledger does not create it.)

### Ledger

`public.deploy_ledger` (created by the runner, `CREATE TABLE IF NOT EXISTS`, no grants to anon/authenticated/admin_api):

```
kind ('migration'|'renumber'), filename, sha256, status ('applied'|'legacy'), git_commit, applied_at; PK (kind, filename)
```

Classification of every candidate: same sha256 in the ledger = skip; **different sha256 = FAIL** (names both hashes); absent
renumber file without the marker `-- deploy-ledger: renumber v1` and not in the seed = FAIL (recovery text below); absent = pending.
All pending files are linted before anything is applied; one bad file fails the run with nothing applied. After any migration is
applied the runner sends `NOTIFY pgrst, 'reload schema'` (only there, never inside migration files).

Each transaction (one per migration; ONE for all pending renumber scripts, so the remap is all-or-nothing) is streamed to
`docker exec -i auth-db psql` on stdin (host files are invisible to psql; `\i` is never used), and inserts its own ledger rows
inside the same transaction. Output is file names, hashes, counts and verdicts only.

## Bootstrap: the legacy seed

Before the ledger existed, older renumber scripts were generated without the marker and may or may not have been run by hand. The
automation must never execute them. `src/auth/migrations/legacy-renumber-seed.tsv` lists every top-level marker-less
`content/_renumber/*.sql` with its sha256, generated mechanically by `just db-seed`.

**Approving the seed (the D2 PR) means exactly one thing: "the deploy automation must never execute these files".** That holds
whatever was or was not run by hand in the past; no audit is required.

On the first run (the ledger has no `legacy` rows) the runner checks the seed covers every marker-less top-level script with a matching
hash. If not, it FAILS before applying or swapping anything. Otherwise it inserts the seed rows as `status='legacy'` in one
transaction. Later seed lines are picked up the same way (any seed row missing from the ledger is inserted as `legacy`).
Legacy rows are never executed.

- A CI check (`.github/workflows/db-seed-check.yml`, runs `bash src/auth/db-deploy.sh seed --check`) fails a PR/push that touches
  these paths if the seed is incomplete. Fix: `just db-seed`, commit.
- Regenerate the seed right before merging the D2 PR (`just db-seed`), so files added meanwhile are included. Files generated by the
  current generator carry the marker and are not seeded; they are applied normally.
- `just db-seed-add <file>` appends ONE top-level script to the seed. Use it only when you have confirmed that script must never
  run (the failure text for an unseeded marker-less file says so). It refuses a file already in the seed with a different hash.
  The usual alternative is to regenerate the script with the current generator.

Recovery text printed for an unseeded marker-less file: *"`<file>` is a pre-ledger renumber script that is not in the seed. Either
regenerate it with the current generator (`just rebuild-carnet ...`) or, ONLY if you have confirmed it must never run, append its
line to src/auth/migrations/legacy-renumber-seed.tsv (`just db-seed-add <file>`)."*

## The lint

Every pending file is linted before apply. It is **defence in depth, not a sandbox**: a hand-written tokeniser, not a SQL parser.
Reviewing PRs that touch these paths is the real control (see privilege note).

Rejected (rule names as printed): any psql meta-command or `:variable` substitution outside quotes (`psql-meta-command`,
`psql-variable`); transaction control (`transaction-control`: BEGIN, START TRANSACTION, COMMIT, END, ROLLBACK, SAVEPOINT, RELEASE,
PREPARE TRANSACTION, including `BEGIN ATOMIC` bodies); `COPY ... TO|FROM|PROGRAM` (`copy`); `ALTER SYSTEM`; `ALTER DATABASE|ROLE|USER ... SET`
(`alter-set`); `LOAD`; `CREATE LANGUAGE`; `LANGUAGE c|internal|...u` (`unsafe-language`); superuser roles; `CREATE EXTENSION` outside the
allowlist (empty for now); server-file functions and roles (`pg_read_file`, `pg_ls_*`, `lo_import`, `lo_export`, `dblink*`,
`pg_{execute,read,write}_server_*`); quoting and encoding settings (`quoting-setting`, `encoding-setting`: `standard_conforming_strings`,
`backslash_quote`, `client_encoding`, `SET NAMES`); structural hazards (`binary-content`: NUL/control bytes/lone CR;
`backslash-quote-in-literal`; `unicode-escape-literal`; `unbalanced-parens`); and, for renumber files, any statement outside the exact
generator shape (`renumber-shape`).

Documented over-strictness (rewrite the SQL; do not expect the lint to change):

- `BEGIN ATOMIC` function bodies are unsupported: write `AS $$ ... $$`. A plain `BEGIN ... END` inside a `$$` body or `DO` is fine.
- `ALTER ROLE/DATABASE ... SET ...` is rejected outright; so is any mention of `client_encoding` or `standard_conforming_strings`,
  even in a string. The `COPY` rule matches the word "copy" anywhere (prose in a literal trips it).
- A dollar quote or `E'..'` string directly after a digit or `$` (`1$$`, `1e'..'`), `SET names = ...` (an UPDATE column called
  `names`), and a UTF-8 character directly followed by a backslash (`é\`) are all rejected or mis-split.
- psql runs with `PGCLIENTENCODING=UTF8` and `PGOPTIONS=-c standard_conforming_strings=on` so role/database defaults cannot change
  how the quotes are scanned, and with `VERBOSITY=terse` so no `DETAIL` (failing rows) is printed. A terse error message can still
  quote a value in rare cases (e.g. a failed cast). On failure only ERROR/FATAL lines are shown.

Commit check: every transaction ends with `\echo DEPLOY_COMMITTED_<random nonce>`. The nonce is only a sanity check, not proof of
COMMIT. Safety rests on psql's exit code plus `verify_ledger` (a ledger row `(kind, filename, sha256, status='applied')` for every
file, read in a separate session after psql exited). Missing nonce or row = hard failure.

## Concurrency

The ledger is read before the lock, so it is re-checked inside the transaction. This IS implemented (not the "PK conflict, re-run"
simplification): each ledger insert is `ON CONFLICT DO NOTHING` inside a CTE so psql `\gset` always gets exactly one row; when a
concurrent run already recorded the file, the runner-emitted `\if :fresh ... \else \echo ... \quit \endif` quits before `COMMIT`
(rollback). The runner then re-reads the ledger, re-classifies and applies what is still pending (up to 3 attempts; still
conflicting = exit 1 "concurrent run; re-run"). Those runner-emitted lines are the only backslash lines psql ever sees. The
workflow's `concurrency` group (queue, never cancel) already serialises deploys; this covers a dispatch alongside, or a manual run.

## Failure table

| Fails at | Result |
|---|---|
| 1 (lint, ledger mismatch, seed gap, migration error) | The failing file changes nothing. No build, no swap. Earlier migrations of the same run stay applied (migrations are additive, harmless). |
| 2 (build) | DB may be ahead by additive migrations; the old site keeps working. |
| 3 (lint or renumber) | The single transaction rolls back; no swap. Old site and old numbering stay consistent. The new image is already built and tagged: do NOT run `docker compose up` by hand (the site would go live on new IDs without the remap); fix and re-run the workflow. |
| 4 (swap, after the retry) | DB is on the new numbering while the old site is live, or the site is down. Re-run the workflow (the ledger skips applied scripts). |

An **auth-db outage fails every deploy closed** (the runner cannot reach the database). That is intended: the site is never swapped
while the DB state is unknown.

## Known limitations

- Reports or stars written between steps 3 and 4 (after the remap, before the new site is live) carry old IDs.
- Tabs opened before the swap: entry pages are NetworkFirst so new loads get the new IDs, but an already-open tab keeps the old ones.
- Offline-downloaded pages keep the old IDs.

`commit_hash` on reports and stars makes all three detectable later.

## Privilege and trust

The runner connects as `gotrue`, which is the **bootstrap SUPERUSER** (`POSTGRES_USER` in `src/auth/docker-compose.yml`), contrary to the
comment in `src/auth/init.sql`. The `deploy` user is in the docker group (effectively root on aretea). The runner adds no privilege, but
it makes the **public repo a channel for production SQL**. The lint narrows what a file can do; it does not make it safe.
Recommendation: branch protection with required review on `src/auth/migrations/**`, `content/_renumber/**` and
`src/auth/db-deploy.sh`.

## Rules for authors

- **Never edit a committed SQL file.** Its sha256 is in the ledger; any change fails every later deploy ("different sha256"). Write
  a follow-up migration instead. (For the same reason `db-seed-add` refuses a changed hash.)
- Only top-level `content/_renumber/*.sql` are applied; anything in subfolders is ignored.
- Migrations: additive and idempotent where reasonable, named `NNNN-name.sql` (`^[A-Za-z0-9._+-]+\.sql$`), no transaction control
  (the runner wraps each in a transaction).

## Emergency manual run

Only if the workflow cannot be used. Lint first (`bash src/auth/db-deploy.sh lint migration <file>`; use `lint renumber <file>` for a
renumber script), then on aretea apply the file and its ledger row as ONE stdin stream, in one transaction, exactly as the runner does
(same psql flags, same advisory lock key 4242). Use `kind` `migration` or `renumber`; `GIT_COMMIT` is the deployed commit:

```
f=src/auth/migrations/NNNN-name.sql; kind=migration; GIT_COMMIT=<commit sha>
sha=$(sha256sum "$f" | cut -c1-64)
{ printf 'BEGIN;\nSELECT pg_advisory_xact_lock(4242);\n'
  cat "$f"
  printf "\nINSERT INTO public.deploy_ledger (kind, filename, sha256, status, git_commit) VALUES ('%s','%s','%s','applied','%s');\nCOMMIT;\n" \
    "$kind" "$(basename "$f")" "$sha" "$GIT_COMMIT"
} | docker exec -i -e PGCLIENTENCODING=UTF8 -e 'PGOPTIONS=-c standard_conforming_strings=on' auth-db \
    psql -X -q -v ON_ERROR_STOP=1 -U gotrue -d gotrue
```

Apply and ledger row commit together or not at all; do not split them into two runs.

## Provenance

The ledger's `git_commit` is the workflow run's `GITHUB_SHA`, which can be older than `origin/main` if pushes queued behind the
concurrency group (the deploy checkout is reset to `origin/main`, the recorded SHA is the one that triggered the run). The frontend's
`GIT_COMMIT` build arg has the same semantics.

## Commands

- `just db-seed` / `just db-seed --check`: write / verify the seed.
- `just db-seed-add <file>`: append one script to the seed (see Bootstrap).
- `DOCKER="sudo docker" just auth-test [name]`: the runner/schema test harness (throwaway postgres + PostgREST containers;
  `src/auth/test/*.test.sh`). Use `DOCKER=docker` where the socket is accessible.
- Helpers: `bash src/auth/db-deploy.sh lint <migration|renumber> <file>`, `renumber-order`, `verify-ledger`.

## Owner follow-up

`src/auth/init.sql` contains `CREATE ROLE ... PASSWORD current_setting('app.postgrest_password')` (and the same for `admin_api`).
That is not valid SQL (PASSWORD takes a literal), so the init script would fail on a fresh volume. Production is unaffected (the
roles exist); fix before rebuilding the database from scratch.
